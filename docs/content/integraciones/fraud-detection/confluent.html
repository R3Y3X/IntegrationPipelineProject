B Tópicos — los dos extremos del pipeline de limpieza

Clúster BeeTech → Tópicos → Schema → Flink → ACLs

Flink necesita que ambos tópicos existan antes de poder crear el statement. Si TransaccionesEnriquecidas-0 no existiera al momento de ejecutar el INSERT INTO, Flink fallaría con un error de tabla no encontrada. Por eso los tópicos se crean primero.

Dependencia crítica con Flink

El statement workshop-clean-transactions-0 hace INSERT INTO `TransaccionesEnriquecidas-0`. Ese tópico destino debe existir antes de que el statement se registre. Si no existe, Flink lanza un error de tabla no encontrada y no puede arrancar.

Este tópico lo creó IBM y lo alimenta el generador de la VM. Llegan transacciones con defectos de formato controlados que el Schema Registry ya acepta como válidos (ver Bloque C).

¿Y el tópico de cada participante?

Cada participante también tiene su propio tópico TransaccionesEvaluadas-NN (con su número de participante). Ese tópico es la salida del pipeline de StreamSets de cada uno — se crea con los mismos parámetros que TransaccionesEnriquecidas-0.

C Schema Registry — contrato sobre los datos sucios

Clúster BeeTech → Tópicos → Schema → Flink → ACLs

Con los tópicos ya creados, IBM registró el schema DirtyTransactionValue sobre TransaccionesSucias-0. Este contrato le dice al Schema Registry qué estructura deben tener los mensajes que produce la VM. Si el productor intentara romper ese contrato, el registro lo rechazaría.

Sin Schema Registry

  • Productor cambia un campo → Flink falla en silencio
  • No hay historial de versiones del schema
  • Bytes sin contexto: Flink no sabe qué estructura esperar

Con Schema Registry

  • Cambios incompatibles rechazados antes de llegar a Flink
  • Historial de versiones con evolución controlada
  • Mensajes Avro con ID de schema embebido — Flink los deserializa automáticamente

D Flink SQL — el puente de limpieza del linaje

Clúster BeeTech → Tópicos → Schema → Flink → ACLs
FROM TransaccionesSucias-0 datos crudos de la VM
statement workshop-clean-transactions-0 BTRIM · UPPER · TRY_CAST · CASE
INSERT INTO TransaccionesEnriquecidas-0 datos limpios → consumer group

Con el clúster, los dos tópicos y el schema en su lugar, IBM creó el statement continuo que conecta el linaje: lee los mensajes crudos de TransaccionesSucias-0, aplica las funciones de limpieza y escribe el resultado normalizado en TransaccionesEnriquecidas-0. Ese statement corre ininterrumpidamente en estado RUNNING.

Por qué Flink va después de los tópicos

Flink interpreta la cláusula INSERT INTO `TransaccionesEnriquecidas-0` como una tabla de destino. Si ese tópico no existiera al registrar el statement, Flink lanzaría Table not found y el pipeline no arrancaría. Los tópicos son siempre prerrequisito del statement.

Campo de entradaProblema típicoFunción Flink SQLCampo de salida

Statement completo

INSERT INTO `TransaccionesEnriquecidas-0`
SELECT
  UPPER(REGEXP_REPLACE(BTRIM(transaction_id_raw), '[^A-Za-z0-9]+', '-'))   AS transaction_id,
  TRY_CAST(
    REPLACE(REGEXP_REPLACE(BTRIM(amount_raw), '[^0-9,.-]', ''), ',', '.')
    AS DOUBLE)                                                              AS amount,
  UPPER(BTRIM(currency_raw))                                               AS currency,
  LOWER(BTRIM(customer_email_raw))                                         AS customer_email,
  UPPER(BTRIM(customer_country_raw))                                       AS customer_country,
  CASE UPPER(BTRIM(account_status_raw))
    WHEN 'ACTIVE'   THEN 'ACTIVE'  WHEN 'ACTIVO'  THEN 'ACTIVE'
    WHEN 'ENABLED'  THEN 'ACTIVE'  WHEN 'INACTIVE' THEN 'INACTIVE'
    WHEN 'INACTIVO' THEN 'INACTIVE' WHEN 'DISABLED' THEN 'INACTIVE'
    ELSE 'UNKNOWN'
  END                                                                      AS account_status,
  source_event_id, source_system, source_sequence, ingestion_time, quality_hints
FROM `TransaccionesSucias-0`
WHERE transaction_id_raw IS NOT NULL;

Lo que acabás de ver en el linaje

Con este statement activo, el linaje queda completo en el tramo de limpieza: VM → TransaccionesSucias-0 → workshop-clean-transactions-0 → TransaccionesEnriquecidas-0. El consumer group fraud-demo-0 y StreamSets leen desde ese último tópico.

E API Key y permisos ACL — quién lee y quién escribe

Clúster BeeTech → Tópicos → Schema → Flink → ACLs

El último paso es asegurarse de que cada participante solo pueda interactuar con sus propios recursos. Cada API Key tiene ACLs que le permiten leer el tópico compartido de salida de Flink y escribir únicamente en su propio tópico.

API Key participante → READ Topic: TransaccionesEnriquecidas-0 (salida de Flink)
API Key participante → WRITE Topic: TransaccionesEvaluadas-NN (tópico personal)
API Key participante → READ Group: streamsets-consumer-NN

Pasos para verificar los permisos

  1. 1 Navegá a BeeTech → Data Integration → API Keys. Localizá la key asignada a tu número de participante.
  2. 2 Hacé clic en tu API Key → pestaña ACLs: debe tener READ sobre TransaccionesEnriquecidas-0 y WRITE sobre TransaccionesEvaluadas-NN.

Paso 6 — Validar contrato y lineage

  1. Abre el Data Contract de TransaccionesEnriquecidas-0.
  2. Confirma que monto, coordenadas y riesgo sean numéricos.
  3. Regresa a Topics y abre TransaccionesEnriquecidas-0.
  4. En la pestaña Overview, baja hasta la sección Stream Lineage y haz clic en View full lineage.
  5. Comprueba el recorrido TransaccionesSucias-0 → workshop-clean-transactions-0 (Flink) → TransaccionesEnriquecidas-0. Si no ves nodos, amplía la ventana de tiempo a Last 10 minutes o Last 24 hours y confirma que hay mensajes recientes en los tópicos.
  6. Actualiza Messages y verifica que el offset continúa avanzando.
  • El statement está en ejecución.
  • La salida cumple el contrato estricto.
  • El lineage muestra la limpieza compartida.
  • Hay datos recientes listos para los pipelines individuales.
