Paso 4 — Observar el statement de Flink

  1. Abre Flink desde la navegación del ambiente.
  2. Localiza workshop-clean-transactions-0.
  3. Confirma que el estado sea RUNNING.
  4. Revisa cómo el SQL usa TRIM, normalización de casing y TRY_CAST.
INSERT INTO `TransaccionesEnriquecidas-0`
SELECT
  UPPER(REGEXP_REPLACE(BTRIM(transaction_id_raw), '[^A-Za-z0-9]+', '-')) AS transaction_id,
  TRY_CAST(REPLACE(REGEXP_REPLACE(BTRIM(amount_raw), '[^0-9,.-]', ''), ',', '.') AS DOUBLE) AS amount,
  LOWER(BTRIM(customer_email_raw)) AS customer_email
FROM `TransaccionesSucias-0`
WHERE transaction_id_raw IS NOT NULL;

B Creación de tópicos

Se crearon dos tópicos principales. TransaccionesSucias-0 lo gestiona IBM (tópico de entrada). Cada participante crea su propio tópico de salida TransaccionesEvaluadas-NN.

Pasos para crear un tópico

  1. 1 Navegá a BeeTech → Topics → + Add topic, ingresá el nombre TransaccionesEvaluadas-NN y hacé clic en Create with defaults.
  2. 2 En las opciones avanzadas configurá: Partitions = 3, Replication factor = 3, Cleanup policy = delete, Retention = 7 días.
  3. 3 Hacé clic en Save & create. Verificá que el tópico aparezca en la lista con las 3 particiones.

C Schema Registry — Data Contract

IBM registró el schema DirtyTransactionValue para el tópico TransaccionesSucias-0. Todos los campos de negocio llegan como texto nullable con defectos intencionales — el Schema Registry garantiza que el productor siempre respete este contrato.

Sin Schema Registry

  • Productor cambia un campo → consumidor se rompe en silencio
  • No hay historial de versiones del schema
  • Bytes sin contexto: el consumidor no sabe qué estructura esperar

Con Schema Registry

  • Cambios incompatibles rechazados automáticamente
  • Historial de versiones con lineage
  • Mensajes Avro con ID de schema embebido

D Flink SQL — statement de limpieza

IBM creó el statement continuo workshop-clean-transactions-0 que corre en estado RUNNING. Lee de TransaccionesSucias-0, aplica las transformaciones y publica en TransaccionesEnriquecidas-0.

Tabla de transformaciones

Campo origenProblema típicoFunción Flink SQLResultado limpio

INSERT INTO `TransaccionesEnriquecidas-0`
SELECT
  UPPER(REGEXP_REPLACE(BTRIM(transaction_id_raw), '[^A-Za-z0-9]+', '-'))   AS transaction_id,
  TRY_CAST(
    REPLACE(REGEXP_REPLACE(BTRIM(amount_raw), '[^0-9,.-]', ''), ',', '.')
    AS DOUBLE)                                                              AS amount,
  UPPER(BTRIM(currency_raw))                                               AS currency,
  LOWER(BTRIM(customer_email_raw))                                         AS customer_email,
  UPPER(BTRIM(customer_country_raw))                                       AS customer_country,
  CASE UPPER(BTRIM(account_status_raw))
    WHEN 'ACTIVE'   THEN 'ACTIVE'  WHEN 'ACTIVO'  THEN 'ACTIVE'
    WHEN 'ENABLED'  THEN 'ACTIVE'  WHEN 'INACTIVE' THEN 'INACTIVE'
    WHEN 'INACTIVO' THEN 'INACTIVE' WHEN 'DISABLED' THEN 'INACTIVE'
    ELSE 'UNKNOWN'
  END                                                                      AS account_status,
  source_event_id,
  source_system,
  source_sequence,
  ingestion_time,
  quality_hints
FROM `TransaccionesSucias-0`
WHERE transaction_id_raw IS NOT NULL;

E API Key y permisos ACL

Cada participante recibe una API Key con permisos ACL exactos sobre su tópico de salida. Esto garantiza que nadie pueda leer ni escribir en los tópicos de otros participantes.

API Key: ABCD1234… → READ Topic: TransaccionesEnriquecidas-0
API Key: ABCD1234… → WRITE Topic: TransaccionesEvaluadas-NN
API Key: ABCD1234… → READ Group: streamsets-consumer-NN

Pasos para verificar los permisos

  1. 1 Navegá a BeeTech → Data Integration → API Keys. Localizá la key asignada a tu número de participante.
  2. 2 Hacé clic en tu API Key y verificá la pestaña ACLs: debe tener READ sobre TransaccionesEnriquecidas-0 y WRITE sobre TransaccionesEvaluadas-NN.
