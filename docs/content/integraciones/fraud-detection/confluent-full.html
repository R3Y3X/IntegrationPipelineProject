Confluent Cloud — Fase 1

El caso de uso: detección de fraude en tiempo real

Cada segundo se procesan miles de transacciones financieras alrededor del mundo. El fraude no avisa — ocurre en milisegundos, y el daño se consolida antes de que cualquier reporte nocturno lo detecte.

En este bootcamp vas a construir la capa de datos en tiempo real que hace posible detectar ese fraude antes de que la transacción sea aprobada. El flujo es el siguiente:

1

VM generadora de transacciones sucias

Una VM simuladora publica eventos Avro al tópico TransaccionesSucias-0. Cada mensaje contiene campos con defectos intencionales: montos como texto con símbolos, IDs con espacios, fechas con formatos inconsistentes.

→
2

Flink SQL limpia el stream

Apache Flink lee TransaccionesSucias-0 en tiempo real, aplica transformaciones SQL (TRIM, UPPER, CAST, REGEXP_REPLACE) y publica transacciones normalizadas en un tópico limpio.

→
3

Pipeline de scoring (StreamSets)

Tu pipeline consume las transacciones ya limpias, aplica reglas de scoring y clasifica cada una como NORMAL, SOSPECHOSA o FRAUDULENTA antes de publicar el resultado.

→
4

Decisión con IA (Orchestrate)

Un agente de watsonx Orchestrate consulta los resultados en lenguaje natural: "¿Cuántas transacciones fraudulentas hubo en los últimos 5 minutos en Brasil?"

Paso 1 Exploración del clúster

Un clúster de Kafka es el conjunto de brokers que almacena y distribuye los eventos. Es la unidad de despliegue fundamental en Confluent Cloud — todo tópico, schema y conector vive dentro de un clúster.

Demostración IBM

IBM navega el clúster compartido Cluster Beetech. Los participantes observan la configuración preexistente antes de crear sus propios recursos.

Conceptos clave del clúster

Broker

Servidor individual del clúster. Almacena particiones de tópicos y atiende solicitudes de producers y consumers.

Partición

Unidad de almacenamiento y paralelismo. Cada tópico tiene N particiones; dentro de cada partición los mensajes están ordenados por offset.

Offset

Número secuencial único de cada mensaje dentro de una partición. Los consumers guardan su posición de lectura usando el offset.

Replication factor

Cantidad de copias de cada partición distribuidas en distintos brokers. Un factor de 3 garantiza tolerancia a fallos de hasta 2 brokers.

Paso 3 Schema Registry — Data Contract

Los tópicos de Kafka almacenan bytes crudos. Sin un contrato de datos, cualquier productor puede publicar cualquier estructura — rompiendo silenciosamente a todos los consumidores. El Schema Registry centraliza y valida los esquemas, garantizando compatibilidad entre versiones.

Sin Schema Registry

  • Productor cambia un campo → consumidor se rompe en silencio
  • No hay historial de versiones de esquema
  • Bytes sin contexto: el consumidor no sabe qué leer
  • Imposible hacer rolling upgrades seguros

Con Schema Registry

  • Cambios incompatibles son rechazados automáticamente
  • Historial completo de versiones con lineage
  • Mensajes Avro/Protobuf con ID de schema embebido
  • Evolución controlada con modos BACKWARD / FORWARD / FULL

Paso 4 Limpieza de transacciones con Flink SQL

Los mensajes en TransaccionesSucias-0 llegan con defectos intencionales. Flink SQL lee el stream en tiempo real y aplica transformaciones declarativas — sin detener el flujo — para producir transacciones normalizadas y listas para el pipeline de scoring.

Demostración IBM — observá el proceso

IBM ejecuta estas consultas en vivo. Tu tarea en esta fase es entender qué limpia Flink y por qué cada transformación es necesaria. En StreamSets vas a consumir el resultado ya limpio.

¿Qué limpia Flink?

Cada campo _raw del schema tiene un defecto distinto. Flink aplica una función específica para normalizar cada uno:

Campo origenProblema típicoFunción Flink SQLResultado limpio
amount_raw"$1.234,56 USD"CAST(REGEXP_REPLACE(…) AS DECIMAL)1234.56
currency_raw" usd "UPPER(TRIM(…))"USD"
transaction_id_raw"txn 00123 abc"UPPER(TRIM(REPLACE(…,' ','')))"TXN00123ABC"
customer_email_raw" USER@DOMAIN.COM "LOWER(TRIM(…))"user@domain.com"
event_time_raw"2024-01-15t10:30:00z"TO_TIMESTAMP(UPPER(TRIM(…)))2024-01-15T10:30:00Z
customer_risk_score_raw"75%" / "score:75"CAST(REGEXP_REPLACE(…,'[^0-9]','') AS INT)75
account_status_raw"ACTIVO" / "enabled"CASE UPPER(TRIM(…)) WHEN … END"ACTIVE"

Consulta Flink — limpieza completa del stream

Esta consulta lee de TransaccionesSucias-0 y publica transacciones normalizadas en el tópico limpio que consumirá tu pipeline de StreamSets:

INSERT INTO TransaccionesLimpias
SELECT
  source_event_id,
  -- IDs: quitar espacios y normalizar a mayúsculas
  UPPER(TRIM(REPLACE(transaction_id_raw, ' ', '')))   AS transaction_id,
  UPPER(TRIM(REPLACE(customer_id_raw,    ' ', '')))   AS customer_id,
  UPPER(TRIM(REPLACE(card_id_raw,        ' ', '')))   AS card_id,
  -- Monto: eliminar símbolos y convertir a numérico
  CAST(
    REGEXP_REPLACE(
      REPLACE(REPLACE(amount_raw, '$', ''), ',', '.'),
    '[^0-9.]', '') AS DECIMAL(18,2))                  AS amount,
  -- Moneda y ubicación: normalizar casing
  UPPER(TRIM(currency_raw))                           AS currency,
  INITCAP(TRIM(location_raw))                         AS location,
  -- Coordenadas: limpiar y convertir a DOUBLE
  CAST(TRIM(lat_raw) AS DOUBLE)                       AS lat,
  CAST(TRIM(lon_raw) AS DOUBLE)                       AS lon,
  -- Tiempo del evento: normalizar a timestamp
  TO_TIMESTAMP(UPPER(TRIM(event_time_raw)),
    'yyyy-MM-dd''T''HH:mm:ss''Z''')                   AS event_time,
  -- Datos del cliente
  TRIM(REGEXP_REPLACE(customer_name_raw, '\\s+', ' ')) AS customer_name,
  LOWER(TRIM(customer_email_raw))                     AS customer_email,
  UPPER(TRIM(customer_country_raw))                   AS customer_country,
  -- Score: extraer dígitos y convertir a entero
  CAST(REGEXP_REPLACE(customer_risk_score_raw,
    '[^0-9]', '') AS INT)                             AS customer_risk_score,
  -- Estado de cuenta: normalizar sinónimos
  CASE UPPER(TRIM(account_status_raw))
    WHEN 'ACTIVE'   THEN 'ACTIVE'
    WHEN 'ACTIVO'   THEN 'ACTIVE'
    WHEN 'ENABLED'  THEN 'ACTIVE'
    WHEN 'INACTIVE' THEN 'INACTIVE'
    WHEN 'INACTIVO' THEN 'INACTIVE'
    WHEN 'DISABLED' THEN 'INACTIVE'
    ELSE 'UNKNOWN'
  END                                                 AS account_status,
  -- Metadatos de trazabilidad
  source_system,
  source_sequence,
  ingestion_time,
  quality_hints
FROM TransaccionesSucias-0;

Paso 5 API Key y permisos ACL

Para que tu pipeline de StreamSets pueda conectarse a Confluent Cloud, necesita credenciales con los permisos exactos sobre los tópicos que va a consumir y producir. Estos permisos se gestionan con ACLs (Access Control Lists) por API Key.

Credenciales por correo

IBM enviará las credenciales de cada participante antes del inicio del bootcamp. No hay valores en esta página — todo lo que necesitás llega en el correo con el asunto "Bootcamp Beetech — Credenciales Confluent".

¿Qué es una ACL en Kafka?

Una ACL define qué operaciones puede realizar un principal (tu API Key) sobre un recurso (tópico, consumer group, clúster). Ejemplo de la estructura:

API Key: ABCD1234... → READ Topic: TransaccionesSucias-0
API Key: ABCD1234... → WRITE Topic: fraud-results-NN
API Key: ABCD1234... → READ Group: streamsets-consumer-NN
