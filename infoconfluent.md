PROBLEMATIZACIÓN BASE Y PROPUESTA DE VALOR1.1 El Dilema del Dato Desactualizado (The "Why")Para enganchar de inmediato tanto al perfil ejecutivo como al técnico, la narrativa se abre con la pregunta de negocio fundamental:"¿Cruzarías una calle transitada basándote únicamente en una foto de los autos que pasaron ayer?"Probablemente no. Sin embargo, la mayoría de las empresas siguen tomando decisiones críticas en producción usando arquitecturas por lotes (batch processing) o reportes nocturnos. El problema central de las organizaciones no es de volumen técnico, sino de velocidad de reacción:"El reporte llega mañana:" Se toma una decisión estratégica cuando la oportunidad de mercado ya pasó."No detecté el fraude a tiempo:" La transacción maliciosa se analiza horas después de haber sido procesada."El cliente ya se fue:" La oferta personalizada se envía cuando el usuario ya cerró la aplicación.La solución es migrar de una arquitectura pasiva a una Arquitectura Dirigida por Eventos (Event-Driven Architecture - EDA) impulsada por procesamiento en tiempo real (Event Streaming).1.2 Estrategia de Abordaje según Perfil de Cliente                       +-----------------------------------+

Clientes Pre-believers (Sin EDA previa):Diagnóstico: No saben que necesitan Kafka o Confluent; describen síntomas operativos ("procesos lentos", "sistemas desalineados").Enfoque: Venta orientada a casos de uso de negocio (ej: detección de fraude en segundos, visión 360° del cliente, inventarios sincronizados).Clientes Pre-believers Técnicos (Usuarios de Kafka Open Source / Self-Managed):Diagnóstico: Ya operan Apache Kafka de forma manual en Kubernetes o infraestructura local, pero sufren por la complejidad de parches, balanceo de particiones, falta de gobernanza y altos costos operativos ("Kafka consume al equipo").Enfoque: Demostrar los beneficios de la plataforma totalmente administrada en la nube (SaaS): reducción del TCO (Total Cost of Ownership), escalabilidad elástica, gobernanza nativa y cero sobrecarga operativa.2. ¿QUÉ ES CONFLUENT? (LA TRÍADA TECNOLÓGICA & SAAS)Confluent Cloud no es solo "un Kafka hospedado"; es una plataforma SaaS empresarial completa para el flujo continuo de datos (Data Streaming Platform) que integra tres pilares tecnológicos bajo un marco unificado de gobernanza y seguridad corporativa:+---------------------------------------------------------------------------------+
|                                CONFLUENT CLOUD                                  |
|                 (Plataforma SaaS Administrada Enterprise)                       |
+---------------------------------------------------------------------------------+
|  1. APACHE KAFKA        |  2. APACHE FLINK           |  3. APACHE ICEBERG       |
|  (Event Streaming Core) |  (Stream Processing)       |  (Open Table Lakehouse)  |
+---------------------------------------------------------------------------------+
|                        STREAM GOVERNANCE & SECURITY                             |
|         Schema Registry | Data Contracts | Stream Lineage | ACLs & RBAC         |
+---------------------------------------------------------------------------------+
1. Apache Kafka (Event Streaming Core): El motor pub/sub distribuido que actúa como el sistema nervioso central, ingiriendo y distribuyendo eventos a escala de Terabytes con ultra baja latencia.2. Apache Flink (Stream Processing Native): El motor de procesamiento distribuido en tiempo real que permite filtrar, transformar, agregar y unir datos en movimiento (stateful stream processing) utilizando SQL declarativo de baja latencia.3. Apache Iceberg (Data Lakehouse Open Table Format): La integración nativa que permite exponer los eventos de los tópicos directamente hacia formatos de tabla abiertos (Tableflow), unificando el mundo del streaming en tiempo real con los motores analíticos del Data Lakehouse sin duplicar datos ni requerir pipelines ETL complejos.Gobierno y Mantenimiento SaaS: Confluent abstrae la infraestructura subyacente entregando disponibilidad del 99.99% (SLA), auto-scaling, balanceo automático de datos en particiones y capas de almacenamiento multinivel (Kora Engine + Tiered Storage).3. ESPECIFICACIÓN TÉCNICA DE COMPONENTES DE CONFLUENT3.1 Tipos de ClustersConfluent Cloud ofrece distintos tipos de clusters adaptados a la madurez y volumen del cliente:Basic: Para entornos de desarrollo, pruebas iniciales y POCs sin costo fijo por hora.Standard: Diseñado para cargas de trabajo de producción ligeras/medianas sin límites de almacenamiento y con escalamiento elástico.Enterprise: Para cargas críticas empresariales que requieren soporte de Private Link, multi-zona de disponibilidad y funciones avanzadas de seguridad.Dedicated: Clusters aislados de alto rendimiento para rendimiento masivo garantizado (MB/s dedicados) e integración con redes corporativas privadas (VPC Peering / Transit Gateway).Freight: Optimizado para la ingesta masiva de datos en lote/históricos de bajo costo donde la latencia extrema no es el factor principal.3.2 Tópicos y Configuraciones AvanzadasLos tópicos son las categorías o canales lógicos donde se almacenan los registros de eventos de forma ordenada e inmutable.Particiones (Partitions): Unidad fundamental de paralelismo y escalabilidad. Permite distribuir la carga de lectura y escritura entre múltiples brokers.Estrategias de Retención:Retención por Tiempo (retention.ms): Define cuánto tiempo permanece un mensaje en el tópico antes de ser eliminado (ej: 7 días, o retención infinita con Tiered Storage).Retención por Tamaño (retention.bytes): Límite de bytes acumulados por partición.Compactación de Logs (cleanup.policy=compact): En lugar de borrar registros antiguos por tiempo, conserva únicamente el último valor conocido para cada clave (Key). Ideal para mantener estados o tablas de dimensión actualizadas.3.3 Schema Registry y Data ContractsEl Schema Registry es el componente de gobernanza central que actúa como el "contrato de interfaz" entre productores y consumidores.[Productor] ---> (1. Consulta/Registra Esquema) ---> [Schema Registry]
     |                                                      |

     v                                                      v
[Tópico de Kafka] ------------------------------------> [Consumidor]
  (Solo Bytes)                                      (Deserializa Bytes)
Principio Fundamental de Datos:Los tópicos de Kafka no entienden de tipos de datos; solo almacenan BYTES. Son los clientes (productores y consumidores) quienes deben encargarse de la serialización y deserialización de esos bytes mediante esquemas validados.Formatos Soportados:Apache Avro: Formato binario compacto de alto rendimiento con esquemas fuertemente tipados.JSON Schema: Estándar flexible basado en JSON para fácil legibilidad y compatibilidad web.Protobuf (Protocol Buffers): Estándar de Google binario y liviano de alta velocidad.Reglas de Evolución de Esquemas (Data Contracts):Para evitar romper aplicaciones consumidoras en producción al modificar la estructura de un dato, el Schema Registry aplica reglas estricta de compatibilidad:BACKWARD (Compatible hacia atrás): El consumidor con el esquema nuevo puede leer datos producidos por el esquema anterior. (Permite actualizar los consumidores primero).FORWARD (Compatible hacia adelante): El consumidor con el esquema anterior puede leer datos producidos con el esquema nuevo. (Permite actualizar los productores primero).FULL: Garantiza compatibilidad bidireccional (FORWARD + BACKWARD).NONE: Sin validación de compatibilidad (no recomendado para entornos de producción).3.4 Conectores, Productores y Grupos de ConsumoFully Managed Connectors: Más de 120+ conectores preconstruidos en la nube para ingestar (Source Connectors) o exportar (Sink Connectors) datos sin escribir código (ej: PostgreSQL CDC, Oracle, AWS S3, Snowflake, Salesforce, Elasticsearch).Productores (Producers): Aplicaciones que publican eventos en los tópicos, encargadas de definir la Clave (Key), el Valor (Value) y aplicar la clave de particionamiento.Grupos de Consumo (Consumer Groups): Conjunto de consumidores que colaboran para leer un tópico. Cada partición del tópico es asignada a un único consumidor dentro del grupo, garantizando el balanceo de carga y el procesamiento paralelo dinámico sin duplicar lecturas.3.5 Seguridad, Permisos y GobernanzaAPI Keys (Key + Secret): Mecanismo principal de autenticación para que las aplicaciones e integraciones interactúen con la API del cluster de Confluent.ACLs (Access Control Lists): Reglas granulares de autorización que definen quién (Principal/Service Account) puede realizar qué operación (READ, WRITE, DESCRIBE) sobre qué recurso (Topic, Group, TransactionalID).RBAC (Role-Based Access Control): Asignación de roles predefinidos a nivel de organización, entorno o cluster (ej: EnvironmentAdmin, DeveloperRead, DeveloperWrite).Stream Lineage: Gráfico interactivo que muestra la trazabilidad visual completa del dato desde la fuente de origen, pasando por transformaciones de Flink, hasta los destinos finales.4. SELECT 
    t.usuario_id,
    t.monto,
    t.ubicacion_actual,
    p.ubicacion_anterior,
    TIMESTAMPDIFF(MINUTE, p.fecha_hora, t.fecha_hora) AS diferencia_minutos
FROM transacciones_stream t

    ON t.usuario_id = p.usuario_id

  AND TIMESTAMPDIFF(MINUTE, p.fecha_hora, t.fecha_hora) < 10;
